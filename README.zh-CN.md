# Loop Engineering Orchestrator（多智能体工程闭环编排）

[English](README.md) | **简体中文**

**一个把多智能体混战变成可控工程闭环的 Agent Skill。**

没有代码,没有框架,没有 SDK——只是一组 markdown 文件,教会你的 AI Agent 如何运转一个文档驱动、证据验收的多智能体项目:输入快照、写入租约、标准回执、独立验收、人工决策闸门,一样不少。

它提炼自一个真实的生产项目:一个由多个 Codex Agent 对话端到端协作建成的客服对话标注平台,用的正是这套闭环。

---

## 要解决的问题

只要试过让几个 AI Agent 对话同时推进一个项目,你大概率遇到过这些:

- 两个 Agent 改同一个文件,悄无声息地互相覆盖。
- 某个 Agent 宣布"做完了!"——但没有任何可验证的交付物。
- 某个 Agent 对着一份十分钟前就已改动的需求干了一小时。
- 同一个任务被做了两遍,因为没人记录派发过什么。
- "协调者" Agent 自己下场写业务代码,既当裁判又当运动员。
- 三份文档同时声称自己是"最终版"。
- 项目状态活在聊天记录里,对话一关就死了。

Agent 越多 ≠ 进展越快。没有工程约束,Agent 越多只意味着混乱来得越快。

## 核心思路

这个 skill **不**试图让 Agent 更聪明,而是让项目**在结构上无法以那些常见方式出错**——借用的是分布式系统几十年前就给出的答案:

| 失败模式 | 对应机制 |
| --- | --- |
| 输入过期 | **不可变输入快照**(SHA-256)——输入漂移即触发 `INPUT_STALE` 停工 |
| 重复干活 | **幂等键**(任务 + 快照)——同一份工作永远不会被派发两次 |
| 文件被覆盖 | **写入租约**——一个受控范围,同一时刻只有一个写入者 |
| 假"完成"声明 | **证据验收**——核哈希、核文件清单、复现命令;自然语言永远不是证据 |
| 消息丢失 | **事件优先 + 心跳对账**——直达回执为主,轮询兜底,两条路走同一道验收门 |
| 自主性失控 | **人工决策闸门**——不可逆或语义性决定,必须停下来问人 |
| 状态依赖聊天 | **文件是权威,对话是工人**——长期事实活在文档里,不在上下文窗口里 |

一句话:**文档保存事实,角色承担责任,快照冻结输入,租约隔离写入,证据决定验收,人守住最终决定权。**

## 安装

本 skill 遵循标准的 `SKILL.md` agent-skill 格式。

**Claude Code** —— 把 skill 文件夹复制进 skills 目录:

```bash
# 个人级(所有项目可用)
git clone https://github.com/yujunyi1018-rgb/loop-engineering-orchestrator.git
cp -r loop-engineering-orchestrator/loop-engineering-orchestrator ~/.claude/skills/

# 或项目级
cp -r loop-engineering-orchestrator/loop-engineering-orchestrator .claude/skills/
```

注意路径必须是 `~/.claude/skills/loop-engineering-orchestrator/SKILL.md`——不能多嵌套一层。开启新会话后自动生效。

**Claude.ai** —— 在 **设置 → Capabilities/Features → skills** 中上传打包好的 `.skill` 文件(或整个 skill 文件夹的 zip)。

**Codex CLI / 其他 Agent** —— 大多数支持 `SKILL.md` 格式的 Agent 会读取厂商中立路径 `.agents/skills/`:

```bash
cp -r loop-engineering-orchestrator/loop-engineering-orchestrator .agents/skills/
```

## 用法

这个 skill 不靠命令调用,靠意图触发。直接说这类话即可:

> "根据这份 PRD 建立项目地图和多 Agent 角色。"
>
> "设计一个负责派发任务和验收交付的协调 Agent。"
>
> "我的 Agent 老是互相覆盖文件——审计一下这个 Loop。"
>
> "执行下一个任务波次。"

skill 会把请求路由到三种操作模式之一,并且只加载当前需要的指导文件:

```
loop-engineering-orchestrator/
├─ SKILL.md                          # 必载:核心模型、9 条不变量、
│                                    # 模式路由、人工决策闸门
└─ references/                       # 按需加载
   ├─ establish-loop.md              # 设计/修订 Loop:项目契约、文档地图、
   │                                 # 角色契约、协调者、触发器
   ├─ run-loop.md                    # 执行:快照、派发前检查、任务合同、
   │                                 # 并行波次、回执、验收
   ├─ audit-and-diagnosis.md         # 失败状态、症状→修复的诊断路径、
   │                                 # 完成检查表
   └─ templates.md                   # 可直接套用的骨架:目录树、角色契约、
                                     # 任务合同、回执、状态记录
```

安全关键内容(九条不变量和人工决策闸门)被刻意放在必载的 `SKILL.md` 里,永远不放进按需文件——"按需"意味着"可能不加载",而底线必须在任何模式下都生效。

## 闭环如何运转

两层嵌套的 Loop:

**建立 Loop**(项目启动时跑一次,重大修订时再跑)——把一个想法变成项目操作系统:

```
用户讨论 → PRD → 项目地图与权威结构
→ 项目记忆与新对话入口 → Agent 角色契约
→ 协调者与触发器设计 → 可执行的项目基线
```

**执行 Loop**(持续运转)——把事件变成经过验证的进展:

```
输入变化或交付事件 → 稳定快照 → 前置检查
→ 任务合同与写入租约 → 范围内执行与最小验证
→ 标准回执 → 独立验收 → 状态更新与本地检查点
→ 下游派发
```

任何任务派发之前,协调者必须回答十个就绪问题(当前权威输入是什么?租约归谁?什么证据能证明完成?结果能否回滚?……)。任何一问答不上就不许派发——歧义必须在控制面消解,绝不下推给执行 Agent 去即兴决定。

验收是两层的:任务通过自己的冒烟测试即可标记 `DELIVERED`,但它所属的需求要等全链路统一测试通过才能变成 `ACCEPTED`。一屏绿色的 DELIVERED 不等于需求完成,skill 会强制把这个区分写进状态记录。

## 这个 skill 不是什么

- **不是"AI 全自动包办一切"的自主系统。** 重大语义与不可逆决策永远停在人工闸门前。自主性从不扩大项目权限。
- **不是并行度放大器。** 它明确优化的是清晰的所有权和可验证的交付,而不是同时在跑的 Agent 数量。
- **不是软件。** 没有任何东西需要运行。"编排器"本质上是一个协调对话 + 状态文件 + 可选的心跳——skill 对这个边界直言不讳,并且要求 Loop 自己的状态记录也同样诚实(心跳暂停就必须记录为 `PAUSED`,不许描述成"自主运转中")。

## 出身

这个 skill 提炼自一个真实项目:一个 AI 客服对话标注平台,由多个 Codex Agent 对话(产品规则、架构、后端、前端、基础设施、测试)在一个不写代码的协调 Agent 编排下建成——这里的每一个机制(静默窗口、租约冲突、回执对账、两层验收)都是先有真实翻车,才有对应规则。

它还很年轻,毛边在所难免。issues 就是为此而开的。
